# 0006 — Manual setup outside the IaC boundary

Status: accepted · Date: 2026-09-11

## Context

`ARQUITETURA.md` §9 reserves this ADR to document configuration that lives
outside `infra/` — either because the provider is immature (Supabase) or
because putting the config under Tofu would itself be a risk (the R2
credential, see `infra/README.md`). Neither the remote Supabase project nor
the R2 credential exists yet at the time of writing; this ADR records what
is decided and verifiable in the repo today, and lists explicitly what is
still pending because there is no remote to configure.

## Decision

### Supabase stays out of the IaC boundary

The official Terraform/OpenTofu provider for Supabase does not yet cover
the surface this project needs (auth settings, RLS-aware project
bootstrap) with the stability `CLAUDE.md` §5 demands elsewhere. Rather than
half-automate it and leave a gap nobody notices, Supabase configuration is
done by hand in the dashboard and documented here — the same reasoning ADR
0003 already applied to the signup-mode setting specifically.

### Signup restricted to invitation

Required by ADR 0003 §2: the whole "provisioned inactive" design assumes
nobody can self-serve their way past that gate at the auth layer, and it
also needs the setting itself to not silently drift.

Where it lives:

- **Remote:** Dashboard → Authentication → Sign In / Providers → *Allow new
  users to sign up* → off.
- **Local:** `supabase/config.toml`, `[auth] enable_signup = false`.

The local value is already committed and version-controlled. The remote
value is not — it is a manual dashboard toggle with no test that can assert
it from outside Supabase's own console, which is exactly the property ADR
0003 flags as not verifiable from this repository. Whoever provisions the
remote project sets this by hand as the first step, before inviting anyone.

### First admin bootstrap

Per ADR 0003 §3, run once against the remote, after the migrations have
been applied and after the first real user has signed in (so their
`auth.users` / `profiles` row exists):

```sql
-- Replace the e-mail. Run as the `postgres` role, in the SQL editor.
update public.profiles
   set role = 'admin', is_active = true
 where id = (select id from auth.users where email = 'secretaria@exemplo.org');
```

This is the only authorized manual mutation of `profiles.role` — every
admin after this one is promoted by an existing admin through the normal
policy path (`admin updates profiles`).

### R2 credential

Covered in detail in `infra/README.md` ("Credencial S3-compatible do
bucket"), summarized here because it is the same category of decision as
the two above — configuration that must exist for the system to work but
that intentionally never enters Tofu state or version control:

- Generated by hand in the Cloudflare dashboard (R2 → Manage R2 API
  Tokens), scoped to **Object Read & Write on the specific bucket only**,
  never account-wide.
- Goes straight to Fly secrets on the worker. Never a `.tfvars`, never a
  `.env`, never inside the Tofu state — seed reasoning: `CLAUDE.md` §5.3
  treats secrets as env-var/Fly-secret-only, and putting an R2 credential
  inside a state file that itself lives in R2 is a needless circularity
  (also noted in `infra/README.md`).

## What is still pending

Nothing below has been done — there is no remote Supabase project and no R2
bucket yet (`ESTADO.md`). Listed here so this ADR does not read as a
completed setup log:

- Create the remote Supabase project.
- Set `enable_signup = false` in the remote dashboard (must happen before
  any invitation goes out).
- Apply `infra/main.tf` (`tofu apply`, not run in this session) to create
  the R2 bucket, then generate the scoped R2 API token by hand and load it
  into Fly secrets.
- Run the first-admin `update` statement above, once a real user exists.
- Migrate the Tofu backend to R2-hosted state (`infra/README.md`, and see
  ADR 0007 for why the state bucket is separate from the photos bucket).

## Consequences

- Nobody can `grep` the repo and know whether signup is actually closed or
  whether the R2 token is scoped correctly on the remote — that verification
  gap is the accepted cost of keeping these two systems out of IaC. It is
  mitigated, not eliminated, by writing the exact steps here instead of
  relying on institutional memory.
- If the Supabase provider matures enough to cover auth settings safely,
  revisit this ADR before moving `enable_signup` into Tofu.
